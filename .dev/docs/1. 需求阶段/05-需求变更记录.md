## 文档目的

> 记录需求变更的全生命周期（申请、评审、决策、实施、归档），保证变更可追溯、影响可量化。

## 适用范围

- **适用对象**：产品经理、研发负责人、测试负责人
- **适用场景**：任何对已确认需求的功能/规则/数据调整
- **不适用范围**：Bug 修复（属缺陷管理流程）、纯文案/排版调整

## 详细内容

### 1. 变更分级

| 级别 | 定义 | 示例 | 审批人 |
|------|------|------|--------|
| L1 紧急 | 影响线上、阻塞发布、合规风险 | 支付逻辑错误 | 产品负责人 + 研发负责人 + 测试负责人 |
| L2 重大 | 改变核心功能或数据模型 | 新增核心模块 | 产品负责人 + 研发负责人 |
| L3 一般 | UI/交互/文案调整 | 按钮位置 | 产品负责人 |
| L4 微小 | 错别字、注释 | "登录"→"登入" | 经办人自查 |

### 3. 变更处理流程

```
申请 → 初审 → 影响评估 → 评审会 → 决策 → 实施 → 验证 → 归档
 │       │         │          │        │       │       │      │
 任何人  PM     研发+测试    干系人   PM跟踪  开发    QA    入库
```

### 5. 变更影响评估清单

每次变更**必须**回答：

- [ ] 影响哪些功能模块？
- [ ] 是否涉及数据库 schema 变更？是否需要数据迁移？
- [ ] 是否涉及对外接口变更？是否需要通知调用方？
- [ ] 是否影响现有测试用例？
- [ ] 是否需要更新相关文档？（PRD/SRS/API/数据库/用户手册）
- [ ] 是否需要灰度/开关？
- [ ] 是否需要回滚预案？

### 6. 反模式（禁止）

- ❌ 口头/聊天确认的变更，无书面记录
- ❌ 跳过评审直接开发，事后再补流程
- ❌ 一份变更单包含多个不相关变更
- ❌ L1 变更未走完整审批即上线
