## 文档目的

> 规范 Code Review 流程、清单与严重级别，保障代码质量、知识共享、团队能力对齐。

## 适用范围

- **适用对象**：所有研发（含 PR 作者、评审人）
- **适用场景**：任何合并到主干的代码改动
- **不适用范围**：紧急 Hotfix（事后补评审）

## 详细内容

### 1. 流程

```
创建 PR → CI 自动化检查 → 指定评审人 → 评审 → 修改 → 通过 → 合并
   │              │                │         │        │       │      │
 作者          自动     至少 1 名核心    评审人    作者     ≥1 同意  作者
```

- **必须**通过 CI（编译、单元测试、静态扫描）后再请求评审
- **必须**指定至少 1 名评审人，跨模块改动 ≥ 2 名
- **必须**解决所有阻塞性评论才能合并

### 2. PR 规范

- 单 PR ≤ 500 行变更（含新增、删除）
- 标题遵循 commit 规范：`<type>(<scope>): <subject>`
- `type` 使用英文 Conventional Commits 类型；`scope` 使用英文小写 kebab-case；`subject` 使用中文动词开头，≤72 字符且不加句号
- 描述必须含：动机、主要改动、影响范围、测试方式、关联 Issue/PRD
- 草稿 PR（WIP）禁止合并
- **禁止**包含无关改动（格式化、import 重排）

### 3. 评审清单

#### 3.1 架构与设计

- [ ] 改动是否在正确的模块/层级？
- [ ] 是否引入循环依赖？
- [ ] 是否破坏现有接口契约？是否更新 API 文档？
- [ ] 是否需要新增/修改数据库表？是否更新数据库设计文档？
- [ ] 是否符合 [模块概要设计](../2.%20设计阶段/06-模块概要设计.md) 与 [模块详细设计](../2.%20设计阶段/07-模块详细设计.md)？

#### 3.2 编码规范

- [ ] 命名是否符合 [Java 编码规范](01-Java编码规范.md)？
- [ ] 是否使用构造注入而非字段注入？
- [ ] POJO 是否使用 Lombok `@Data`？
- [ ] 是否使用 `BigDecimal` 处理金额？
- [ ] 是否使用占位符日志而非字符串拼接？
- [ ] 是否输出敏感信息（密码、手机号、身份证）？

#### 3.3 性能

- [ ] 是否引入 N+1 查询？
- [ ] SQL 是否命中索引？
- [ ] 是否在大循环内创建对象？
- [ ] 是否合理使用缓存？key 是否规范？TTL 是否设置？
- [ ] 事务范围是否合理？是否在事务内调用 RPC / MQ？

#### 3.4 安全

- [ ] 入参是否校验（`@Valid`）？
- [ ] 是否使用参数绑定（`#{}`）而非 SQL 拼接？
- [ ] 鉴权 / 越权检查是否完整？
- [ ] 敏感信息是否加密存储？
- [ ] 是否有 XSS / CSRF 防护？

#### 3.5 异常与日志

- [ ] 异常是否被吞掉？
- [ ] 业务异常是否使用 `BizException` + 错误码？
- [ ] 关键路径是否记录 INFO 日志？
- [ ] 异常是否记录 ERROR 日志（含 traceId）？

#### 3.6 测试

- [ ] 是否新增/修改测试用例？
- [ ] 覆盖率是否达标（关键模块 ≥ 85%、普通 ≥ 70%）？
- [ ] 测试是否独立、可重复？
- [ ] 是否覆盖异常流、边界值？

#### 3.7 文档

- [ ] 是否需要更新 [API 设计文档](../2.%20设计阶段/02-API设计文档.md)？
- [ ] 是否需要更新 [数据库设计文档](../2.%20设计阶段/03-数据库设计文档.md)？
- [ ] 是否需要更新 [接口设计文档](../2.%20设计阶段/05-接口设计文档.md)？
- [ ] 是否需要更新 [需求变更记录](../1.%20需求阶段/05-需求变更记录.md)？

### 4. 严重级别

| 级别 | 标识 | 定义 | 处理 |
|------|------|------|------|
| Blocker 🚫 | 必修 | 影响功能、安全、数据正确性 | 必须修改，禁止合并 |
| Major ⚠️ | 必修 | 明显缺陷、性能、违规 | 必须修改，可后置 |
| Minor 💡 | 建议 | 风格、可读性、小优化 | 建议修改，作者决策 |
| Praise 👍 | 鼓励 | 优秀实践可学习 | 表达肯定 |

### 5. 评审反馈规范

- **对事不对人**：评论代码不评论人
- **具体可执行**：避免"这样不好"，应"建议改为 X，原因是 Y"
- **正反示例**：用代码示例说明
- **及时响应**：评审人 4 小时内首次响应，作者 24 小时内回复
- **避免冗长会议**：评审通过异步评论，必要时线下讨论

### 6. 评审人要求

- 熟悉被评审代码所属模块
- 能从架构、规范、安全、性能多角度审视
- 不熟悉的模块必须加领域专家
- 紧急 PR 优先响应，不阻塞业务

### 7. 自动化检查（CI 必须项）

| 检查项 | 工具 |
|--------|------|
| 编译 | Maven |
| 单元测试 | JUnit 5 |
| 覆盖率 | JaCoCo ≥ 70% |
| 静态扫描 | Checkstyle / SpotBugs / SonarQube |
| 提交规范 | commitlint |
| 依赖漏洞 | OWASP Dependency-Check |
| API 兼容性 | swagger-diff |

### 8. 合并策略

- **Squash and merge**：常规功能
- **Rebase and merge**：保留完整历史
- **Merge commit**：长期分支或需要保留分支拓扑时使用。
- 合并后删除远程分支
- 主干（main）必须保持可发布状态

### 9. 反模式（禁止）

- ❌ 自我合并（无评审人同意）
- ❌ 评审人只看标题不看代码
- ❌ 大 PR（> 500 行）一次性评审
- ❌ 评论无具体建议（"这写得不好"）
- ❌ 评审通过后无人合并长期悬挂
- ❌ 跳过 CI 直接合并
