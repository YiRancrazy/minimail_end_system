## 项目初始化自检清单（黄山版）

> 目标：保证项目从零开始即符合阿里巴巴编码规约，降低后期重构风险。  
> 建议搭配 `Alibaba Java Coding Guidelines` 插件（IDEA / Eclipse）使用，部分强制规约可由插件自动检测。

---

### 一、工程结构与目录划分

- [ ] **单一应用**统一使用 `{公司域名}.{应用名}` 作为顶层包名（如 `com.yirancrazy.minimall`）
- [ ] 核心模块划分清晰，至少包含：
  - `controller` – 控制器层（对应用协议，不掺杂业务逻辑）
  - `service` – 业务逻辑层（接口与实现分离）
  - `manager` – 通用业务处理层（可下沉对第三方、DAO的组合操作）
  - `dao / mapper` – 数据访问层（仅负责数据存取）
  - `domain / model` – 领域模型包（按规约定义 PO / DO / DTO / VO / Query / AO）
- [ ] 各层之间严格单向依赖：上层依赖下层，禁止反向依赖
- [ ] 资源文件按 `resources/{env}` 管理多环境配置（dev / test / prod）
- [ ] 配置文件与代码分离，敏感信息（密码、密钥）不得硬编码，使用配置中心或环境变量

---

### 二、命名与代码风格

- [ ] 类名使用 `UpperCamelCase`；方法名、参数名、变量名使用 `lowerCamelCase`
- [ ] 常量全部大写，单词间下划线分隔，力求语义完整（`MAX_RETRY_TIMES`）
- [ ] POJO 类中布尔类型变量 **不加 `is` 前缀**（否则部分框架解析引起序列化错误）
- [ ] 抽象类以 `Abstract` 或 `Base` 开头；异常类以 `Exception` 结尾；测试类以 `Test` 结尾
- [ ] 数组定义使用 `String[] args` 而非 `String args[]`
- [ ] 所有覆写方法必须加 `@Override` 注解
- [ ] 已导入 IDEA / Eclipse 团队统一的 `codeStyle` 模板文件（基于阿里规约）
- [ ] 已集成 `p3c-pmd` 或 `checkstyle` 自定义规则，并在 CI 流程中检查

---

### 三、Maven / Gradle 构建配置

- [ ] 父子模块统一版本管理，禁止子模块显式声明版本号（通过 `<dependencyManagement>`）
- [ ] 使用 `${revision}` 统一管理版本，避免子模块硬编码
- [ ] `pom.xml` / `build.gradle` 中二方库、三方库版本精确到**三位**（`x.y.z`），禁用 `SNAPSHOT` 用于生产发布
- [ ] 禁止引入有 `RELEASE`、`LATEST` 等动态版本的依赖
- [ ] 明确排除传递依赖中的冲突，并在 `dependency:tree` 检查后固化
- [ ] 打包时指定 `finalName`，遵循 `{app}-{version}.jar` 格式，且包含 `git.commit.id` 信息（插件：`git-commit-id-plugin`）

---

### 四、日志规约

- [ ] 统一使用 **SLF4J** 门面 + **Logback / Log4j2** 实现
- [ ] 类中定义 `private static final Logger logger = LoggerFactory.getLogger(当前类名.class);`
- [ ] 正确使用占位符：`logger.info("orderId: {}", orderId);`，禁止字符串拼接
- [ ] `log4j2.xml` / `logback.xml` 已配置异步日志输出、日志滚动策略、最大保留天数
- [ ] `DEBUG` 级别判断才输出大文本或集合，避免无意义 `toString()` 开销
- [ ] 线上环境禁止输出 `DEBUG` 日志，敏感信息（身份证、手机号、密码）必须脱敏或禁止输出
- [ ] 异常日志必须包含案发现场信息和异常堆栈；`e.getMessage()` 不能单独打，需加上具体变量

---

### 五、异常处理

- [ ] 创建统一的业务异常类（如 `BizException`），继承 `RuntimeException`
- [ ] 统一错误码枚举，定义 `code` 与 `message`，且与前端、调用方约定好国际化方案（可选）
- [ ] 全局异常拦截器（`@ControllerAdvice` + `@ExceptionHandler`）捕获所有未处理异常，返回统一响应结构
- [ ] 不要在循环体内使用 `try...catch`，应在循环外包裹
- [ ] 捕获异常后，若重新抛出，必须保留原始异常链（`throw new BizException("msg", e)`）
- [ ] 禁止 `catch` 后什么都不做（吞掉异常），极特殊情况须有注释说明

---

### 六、数据库与 ORM 规约

- [ ] 表名、字段名必须使用**小写字母/数字**，禁止数字开头，禁止下划线间仅有数字（如 `a_1_b` 不行）
- [ ] 索引命名严格遵循：
  - 主键：`pk_字段名`
  - 唯一索引：`uk_字段名`
  - 普通索引：`idx_字段名`
- [ ] 表必备三字段：`id`（自增/雪花）、`create_time`（或 `gmt_create`）、`update_time`（或 `gmt_modified`）
- [ ] 表达“是/否”的字段使用 `is_xxx` 命名，类型为 `unsigned tinyint`（1=是，0=否）
- [ ] 禁止使用存储过程，禁止使用外键，外键约束在应用层保证
- [ ] 禁止使用 `SELECT *`，查询必须列出具体字段
- [ ] SQL 参数必须使用 `#{}` 占位符，禁止使用 `${}` 拼接用户输入（防注入）
- [ ] 使用 MyBatis-Plus / MyBatis 时，`Mapper` 接口需加 `@Repository` 注解（可选，保证扫描）
- [ ] 数据库连接池配置已优化（Druid），并配置了慢 SQL 监控、连接泄漏检测、StatViewServlet

---

### 七、单元测试与集成测试

- [ ] 单元测试路径与源码保持相同包结构，类名 `XxxTest`
- [ ] 使用 `JUnit5` 或 `TestNG`，Mock 框架可选 `Mockito`
- [ ] 单元测试必须遵守 AIR 原则：全自动、独立、可重复
- [ ] 核心业务逻辑、工具方法必须覆盖单元测试
- [ ] 外部依赖（数据库、Redis、RPC）通过 `Testcontainers` 或嵌入式方案做集成测试，避免依赖本地环境
- [ ] 测试中禁止使用 `Thread.sleep()`，使用 `awaitility` 等待条件
- [ ] 项目已配置 JaCoCo 等覆盖率工具，核心模块行覆盖率不低于 70%（视团队调整）

---

### 八、安全规约

- [ ] 用户请求参数统一使用 JSR-303 校验，禁止空信任客户端数据
- [ ] 敏感数据（身份证、手机号、银行卡）在日志、返回值中脱敏处理
- [ ] SQL 注入防护：MyBatis 禁用 `$`，如需动态表名/字段名，必须白名单校验
- [ ] 避免 XSS：响应头添加 `X-Content-Type-Options: nosniff` 和内容安全策略，富文本过滤
- [ ] 依赖包安全扫描：引入 OWASP Dependency-Check 插件（Maven/Gradle），无高危漏洞
- [ ] 权限验证：每个接口必须进行身份认证和授权（注解 + 拦截器），不可仅靠前端控制

---

### 九、集合与并发处理

- [ ] 集合初始化时指定初始容量（`new ArrayList<>(capacity)`，`new HashMap<>(capacity)`）
- [ ] 禁止在 `foreach` 循环里进行 `remove` / `add` 操作，使用 `Iterator` 或 `removeIf`
- [ ] 使用 `ThreadLocal` 的变量必须及时 `remove()`（通常配合拦截器）
- [ ] `SimpleDateFormat` 线程不安全，必须使用 `DateTimeFormatter` 或 `ThreadLocal` 封装
- [ ] `HashMap` 多线程下改用 `ConcurrentHashMap`，`ArrayList` 改用 `CopyOnWriteArrayList`
- [ ] 锁的使用：`synchronized` 或 `Lock` 必须配对 `try-finally`，避免死锁
- [ ] 线程池必须通过 `ThreadPoolExecutor` 显式创建，禁止使用 `Executors`，明确核心参数

---

### 十、序列化及其他

- [ ] 实现 `Serializable` 的类必须显式指定 `serialVersionUID`，且为 `private static final long`
- [ ] RPC 返回的 POJO 不允许使用 `Hashtable`、`Vector` 等过时集合，使用 `HashMap`、`ArrayList`
- [ ] `BigDecimal` 等值比较使用 `compareTo()`，禁止使用 `equals`（因精度范围不同）
- [ ] 浮点数比较不能使用 `==`，需指定误差范围或转为 `BigDecimal`
- [ ] 所有类必须添加类级别的 Javadoc：功能说明、作者、日期（推荐使用 `@author`、`@since`）
- [ ] 复杂业务逻辑、正则、魔法数字需有注释，注释力求“解释为什么，而非是什么”
- [ ] 已禁用 `e.printStackTrace()`，统一使用日志输出
- [ ] 已添加 `.gitignore`：忽略 IDE 文件、`target` / `build`、`*.log`、环境敏感配置
- [ ] `README.md` 已编写：项目简介、本地启动步骤、依赖中间件清单、架构简图

---

### 使用建议

1. 每完成一项，在 `[ ]` 内打 `x`，生成带状态的报告。
2. 在项目启动会或代码 review 前，将此清单作为基线对项目进行巡检。
3. 配合 IDE 插件 `Alibaba Java Coding Guidelines` 实时检查，减少人工遗漏。
4. 可将本清单导入在线协作文档（语雀/Notion/Confluence），指派负责人和截止日期。

这样一套走下来，项目在起步阶段就具备了清晰的骨架和安全的基线，后续开发只需专注于业务实现，而不会被基础规范问题绊倒。
