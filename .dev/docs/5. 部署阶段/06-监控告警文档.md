## 1. 文档概述

### 1.1 目的
统一项目监控指标、告警规则与处理流程，确保系统异常能被及时发现、快速响应，并严格遵循《阿里巴巴 Java 开发规约（黄山版）》中对日志、异常处理及线上运行的要求。

### 1.2 适用范围
- 所有生产环境（含预发布）Java 应用服务
- 关联中间件（数据库、缓存、消息队列等）
- 基础资源（服务器 CPU、内存、磁盘、网络）

### 1.3 引用规范
- 《阿里巴巴 Java 开发手册（黄山版）》
  - 异常处理章节（强制：捕获异常必须处理或记录完整现场；严禁吞掉异常）
  - 日志规约章节（强制：使用 SLF4J 门面；禁止使用 `System.out` 和 `e.printStackTrace()`；异常信息必须包含案发现场与完整堆栈）
  - 安全规约章节（涉及敏感信息脱敏）

## 2. 监控架构（示意）
- **数据采集**：Filebeat/Agent 采集应用日志；Micrometer + Prometheus 采集 JVM/业务指标；慢查询日志采集。
- **存储分析**：Elasticsearch + Logstash / VictoriaMetrics / Prometheus。
- **告警引擎**：AlertManager / Grafana Alerting / 云厂商监控告警。
- **通知渠道**：企业微信 / 钉钉 / 邮件 / PagerDuty（按级别选用）。

## 3. 监控对象与核心指标

### 3.1 应用服务（Java）
| 指标分类 | 监控项 | 关键阈值/说明 | 规约关联 |
|---------|--------|--------------|----------|
| 存活检测 | 健康检查接口 | 连续失败 2 次 | 必须提供 Readiness/Liveness |
| 错误日志 | `ERROR` 级别日志数量 | 5 分钟内出现任意 `OutOfMemoryError`、`StackOverflowError` 立即告警；ERROR 日志达到 **10 条/分钟** | 强制：Error 日志必须及时监控，严禁忽略 |
| 异常堆栈 | 日志中是否包含 `Caused by` | 若异常未包含堆栈，应视为系统隐患，触发提醒 | 强制：异常必须打印堆栈信息 |
| 业务异常 | 特定业务异常码（如 “ORDER_LOCK_FAIL”） | 自定义阈值 | 强制：异常信息需包含案发现场（如订单 ID）|
| 接口性能 | 请求 QPS、P99 响应时间、错误率 | 错误率 >1%（P2），>5%（P1）；P99 响应时间 >2s 触发告警 | 推荐：关键接口配置监控 |
| JVM 内存 | 堆内存使用率、非堆使用率 | >85% 警告，>95% 严重且触发 dump | 避免 OOM |
| GC | Full GC 频率、GC 暂停时间 | Full GC > 1次/10分钟，单次停顿 >1s | 影响 RT |
| 线程 | 死锁检测、活跃线程数 | 检测到死锁立即 P0 | 服务僵死 |

### 3.2 数据库（MySQL / PostgreSQL）
| 指标 | 监控项 | 告警条件 |
|------|--------|----------|
| 慢 SQL | 执行耗时 > 200ms 的 SQL | 1 分钟内出现 5 条 |
| 连接池 | 活跃连接数 / 总连接数 | >80% P2，满池 P1 |
| 死锁 | 数据库死锁日志 | 出现即告警 P1 |
| 主从延迟 | 同步延迟秒数 | >3s P2 |

### 3.3 中间件（Redis / MQ）
- Redis：连接状态、命中率、内存使用率
- RocketMQ/Kafka：消息积压量、消费延迟

### 3.4 基础设施
- CPU 使用率：>90% P2
- 内存使用率：>85% P2
- 磁盘使用率：>85% P2（日志磁盘单独监控）
- 网络流量：异常突降/突增

### 3.5 监控服务覆盖列表

监控覆盖11个服务：gateway(8080), auth-service(8201), user-service(8202), merchant-service(8203), goods-service(8204), cart-service(8205), order-service(8206), pay-service(8207), stock-service(8208), notify-service(8209), platform-service(8210)
+ 基础设施：MySQL, Redis, Nacos, RocketMQ, Elasticsearch, Nginx

## 4. 告警规则与级别定义

### 4.1 严重等级
| 等级 | 名称 | 响应要求 | 典型场景 |
|------|------|----------|----------|
| P0 | 紧急 | 5 分钟响应，15 分钟止损 | 服务整体不可用；OOM；数据库瘫痪；死锁 |
| P1 | 严重 | 15 分钟响应，1 小时内处理 | 接口错误率 >5%；连接池满；消息大量积压 |
| P2 | 警告 | 30 分钟响应，当天解决 | 错误率 >1%；慢 SQL 暴增；磁盘 >85% |
| P3 | 提醒 | 下一个工作日跟进 | RT 缓慢上升，非关键异常增加 |

### 4.2 关键告警规则样例
```yaml
- alert: JavaErrorLogSpike
  expr: rate(logback_events_total{level="error"}[5m]) > 0.1
  for: 1m
  labels:
    severity: P2
  annotations:
    summary: "应用 {{ $labels.app }} 错误日志激增"
    description: "5 分钟内错误日志数 {{ $value }}，请检查异常堆栈"

- alert: OutOfMemoryError
  expr: increase(log_messages{level="error", message=~".*OutOfMemoryError.*"}[5m]) > 0
  severity: P0
  summary: "检测到 OutOfMemoryError"
```

## 5. 告警通知与升级策略
- **P0**：立即电话 + 即时通讯群通知，若 5 分钟无确认转值班经理。
- **P1**：即时通讯群通知 + 邮件，15 分钟无确认升级至 P0 通知方式。
- **P2/P3**：邮件或日报方式，每日汇总。

## 6. 告警处理流程
1. **告警触发** → 值班人员查看监控大盘，定位异常时间点。
2. **初步排查** → 根据日志（ELK）搜索关联 `traceId` / 关键字，提取案发现场信息（规约要求：日志必须包含可追溯的业务标识）。
3. **应急措施** → 限流、重启、回滚、切流，以恢复服务为优先。
4. **根因分析** → 故障结单后 24 小时内输出报告，记录故障原因、处理步骤及改进项。
5. **改进跟踪** → 更新监控阈值、优化慢 SQL、补充单元测试等。

## 7. 阿里巴巴规约符合性要求
为保证监控告警有效，项目必须落实以下规约（黄山版）条目：

### 7.1 日志规约
- 【强制】应用必须依赖 **SLF4J** 门面，禁止直接使用 Log4j/Logback 原生 API。
- 【强制】生产环境禁止输出 `System.out.println` 或 `e.printStackTrace()`，所有异常必须由日志框架记录，否则监控将无法采集。
- 【强制】日志输出异常时，必须包含 **案发现场信息** 和 **完整异常堆栈**，写法：`log.error("订单处理失败, orderId:{}", orderId, e);`
- 【推荐】谨慎使用 `ERROR` 级别，仅在影响功能正常使用、需要人工介入时才记录 ERROR，避免告警泛滥。
- 【参考】日志文件至少保存 15 天，以便回溯。

### 7.2 异常处理规约
- 【强制】catch 块中绝不允许空处理或仅打印 `e.printStackTrace()`；必须记录错误或重新抛出自定义异常。未记录的异常等于隐形炸弹，监控无法发现。
- 【强制】异常类命名使用 `Exception` 结尾，携带足够上下文。
- 【强制】避免对 `RuntimeException`（如 `NullPointerException`）进行 catch，应通过预检查避免，此类错误应快速暴露并触发 P0/P1 告警。

### 7.3 线上运行规约
- 【强制】生产环境必须配置 **心跳探活** 与 **核心指标监控**。
- 【强制】禁止上线未被监控覆盖的关键业务接口。
- 【推荐】对于慢查询、大对象、大事务进行专项监控，防止 JVM 内存泄漏。
