> 定义版本发布异常时的回滚触发条件、回滚步骤、验证标准与异常处理，作为发布异常的应急手册。

## 2. 回滚触发条件（满足任一即启动）
- [ ] 核心接口 5xx 错误率 > 1%
- [ ] 服务平均响应时间 > 2s 且持续 5 分钟
- [ ] 数据库死锁/慢查询激增，导致业务阻塞
- [ ] 关键业务功能不可用（如登录、下单、支付）
- [ ] 数据一致性问题，如订单金额异常
- [ ] 其他：（自定义）

## 3. 回滚前准备
### 3.1 备份与制品确认
- [ ] **数据库备份**：已对目标库执行全量备份/快照（如 RDS 快照），备份 ID:______
- [ ] **应用制品**：上一版本制品已存在于仓库  
  - JAR/WAR：`xxx-1.x.x.jar`（MD5:______）  
  - Docker 镜像：`registry.cn-xxx/xxx:1.x.x`
- [ ] **配置文件**：已从配置中心（Nacos/Apollo）导出目标版本配置快照
- [ ] **静态资源**：CDN 资源版本已锁定，必要时回退至 `v1.x.x`

### 3.2 依赖与影响评估
- [ ] 下游服务是否已固定版本并可兼容回滚版本  
- [ ] 数据库表结构变更是否可逆（必须有回滚 DDL 脚本）  
- [ ] 消息队列中的未消费消息是否需要清理或重新投递  
- [ ] 回滚是否会影响定时任务/批处理（如有，需同步处理）

## 4. 详细回滚步骤

### 4.1 代码/服务回滚（无状态应用）
> **规约要求**：必须使用 **Git Tag** 或制品仓库中的正式版本，禁止从非受控渠道获取代码/包。

1. **摘除流量**：从负载均衡（SLB/Nginx/网关）摘除待回滚节点。  
2. **部署目标制品**：  
   - CI/CD 方式：触发回滚流水线，选择目标版本制品；  
   - 手动方式：使用 `kubectl set image` / `docker run` 或传统部署脚本，指定目标镜像/JAR。  
3. **健康检查**：启动后检查 `/health`、日志无异常，确认服务已注册到注册中心。  
4. **灰度放开流量**：先放 1% → 10% → 100%，观察监控。  
5. **全量恢复**：全部节点回滚完成。

### 4.2 配置回滚
> **规约要求**：配置变更须通过配置中心，并保留历史版本，一键回滚。  
- 登录 Nacos/Apollo，将变更的配置集回滚至版本 `tag-xxx`。  
- 动态配置项确认已刷新（部分应用需重启或调用 refresh 端点）。  
- 验证配置值是否符合预期（可登录实例查看 `/env` 或日志输出）。

### 4.3 数据库回滚（最严格的环节）
> **规约强制**：  
> - **禁止** 直接在生产环境执行未经验证的回滚 SQL。  
> - 所有 `UPDATE`/`DELETE` 必须带 `WHERE` 条件，并先 `SELECT` 确认影响行数。  
> - 使用事务包裹，确认影响正确后提交。

- 执行回滚脚本清单（见附录）。  
- 执行前验证：`SELECT COUNT(*)` 确认目标数据范围。  
- 在事务中执行 DML 回滚，并校验关键记录。  
- 若存在 DDL 回滚（如删表、删字段），务必确认无数据丢失风险，尽量采用“软删除”（逻辑删除/重命名）而非物理删除。  
- 涉及数据迁移的，需运行对账脚本，确认数据一致性。

### 4.4 缓存与消息队列处理
- **缓存**：清除相关 Redis Key（列出 Key 模式）：  
  ```
  user:session:*, product:detail:*, config:*
  ```
- **消息队列**：  
  - 若存在格式不兼容的消息堆积，需消费/移至死信队列。  
  - 必要时重置消费者位点。

## 5. 回滚验证
| 验证项 | 方法 | 预期结果 | 实际结果 |
|--------|------|----------|----------|
| 核心接口可用性 | 调用 `/api/xxx`，检查状态码 200 | 返回成功 | |
| 数据一致性 | 执行对账 SQL（附录） | 记录数一致 | |
| 错误日志 | 观察 5 分钟内无新增 ERROR | 无致命错误 | |
| 监控指标 | QPS、RT、错误率恢复至基线 | 正常范围 | |
| 配置生效 | 请求返回数据符合回滚配置 | 配置正确 | |

SELECT COUNT(*) FROM t_order_main WHERE status = 1;
COMMIT;
-- 谨慎执行 DDL，需二次确认

### 8.4 遵从规约清单（摘自黄山版）
- 【强制】数据库变更必须提供回滚方案，上线前在测试环境验证回滚脚本。  
- 【强制】禁止在生产环境使用未带 WHERE 条件的 UPDATE/DELETE 语句。  
- 【推荐】利用配置中心版本管理能力回滚配置，避免手动修改文件。  
- 【强制】线上所有变更操作必须保留操作日志，可用于审计追溯。  
- 【推荐】回滚后的代码与制品必须来源于受控仓库（Git Tag + 制品库），杜绝“热修复”包。  
- 【强制】回滚执行过程必须有两人以上在场，一人操作一人复核。
