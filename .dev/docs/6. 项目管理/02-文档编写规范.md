## 文档目的

> 统一项目文档的编写格式、写作风格与维护流程，确保团队所有成员产出的文档结构一致、可读性高、可追溯。

## 适用范围

- **适用对象**：所有参与撰写/评审 `.md` 文档的人员
- **适用场景**：从需求到运维的各阶段文档
- **不适用范围**：代码内注释（见 [Java编码规范](../3.%20开发阶段/01-Java编码规范.md)）、提交信息（见 [Git提交规范](../3.%20开发阶段/06-Git 提交规范.md)）

## 详细内容

### 1. 文档结构规范

#### 1.1 必备章节

所有文档**必须**包含以下五大章节，缺一不可：

| 章节 | 说明 |
|------|------|
| 文档信息 | 表格，描述文档元数据 |
| 文档目的 | 1-3 句话说明"为什么写、谁读、读完获得什么" |
| 适用范围 | 适用对象/场景/版本 + 不适用范围 |
| 详细内容 | 主体内容，按需组织子章节 |
| 相关文档链接 | 上下游 + 横向 + 参考资料 |
| 变更记录 | 表格，日期/版本/变更人/说明 |

#### 1.2 章节命名

- 一级标题：`## 1. xxx`、`## 2. xxx`（带阿拉伯数字编号）
- 二级标题：`### 1.1 xxx`
- 三级标题：`#### 1.1.1 xxx`
- 文档主标题：唯一 `#` 一级，使用文件名同名

### 2. 写作风格规范

#### 2.1 语言

- **必须使用中文**撰写（与代码注释、commit 信息保持一致）
- 英文术语首次出现时给中英对照，例如：**熔断（Circuit Breaker）**
- 后续可直接使用术语表中的标准译法

#### 2.2 措辞分级

| 等级 | 用词 | 含义 |
|------|------|------|
| 强制 | **必须 / 禁止 / 严禁 / 不得** | 违反即不合规 |
| 推荐 | **应当 / 建议 / 推荐** | 默认遵守，偏离需说明理由 |
| 可选 | **可 / 视情况** | 自由裁量 |

- 禁止使用："尽量"、"最好"、"差不多"、"应该可以"等模糊措辞。

#### 2.3 段落组织

- 一段落一主题，单段不超过 8 行
- 关键结论/规则**加粗**或单独成行
- 复杂流程用流程图、表格、列表，禁止长段叙述

#### 2.4 图表使用

- **流程图**：Mermaid 语法（GitHub 原生渲染）
- **架构图**：Mermaid `graph` / `C4` 语法，必要时附 PlantUML
- **表格**：用于对比、字段、状态枚举
- 图片：使用相对路径 `../assets/xxx.png`，文件存于 `assets/` 目录

### 3. 链接与索引规范

#### 3.1 内部链接

- 优先使用相对路径：`[文档名](../2.%20设计阶段/02-API设计文档.md)`
- 路径含空格时用 `%20` 转义或重命名文件（推荐重命名）
- 链接文本使用文档名，不用"点这里"、"详情"等

#### 3.2 索引维护

- 任何文档**新增、删除、重命名**后，**必须**同步更新：
  - 项目根 [CLAUDE.md](../../../../CLAUDE.md)
  - 所在阶段目录的 `README.md`
  - 引用该文档的其他文档

#### 3.3 失效链接检查

- 每次 PR/提交前人工 review 链接有效性
- 可使用 `markdown-link-check` 工具自动检测

### 4. 命名规范

#### 4.1 文件名

- 仅允许：中文、英文、数字、`-`、`.`
- 推荐结构：`<序号>. <文档名>.md` 或 `<文档名>.md`
- 同一目录内文档保持统一风格
- 禁止：`:`、`/`、`?`、`#`、`\`、空格（强烈建议，避免 URL 转义问题）

#### 4.2 目录名

- 一级目录使用阶段名：`1. 需求阶段`、`2. 设计阶段`…
- 二级目录按需创建，需在阶段 `README.md` 中说明

### 5. 变更管理

#### 5.1 变更记录填写

- 每次文档修改**必须**在"变更记录"表追加一行
- 至少包含：日期、版本号（自增）、变更人/角色、变更说明
- 重大变更（推翻既有结论）需在变更说明中标明 ⚠️

#### 5.2 版本号规则

- 主版本（大变更）：V1 → V2
- 次版本（新增章节）：V1.0 → V1.1
- 修订（小修正/排版）：V1.0 → V1.0.1

#### 5.3 评审流程

| 阶段 | 评审人 | 输出 |
|------|--------|------|
| 草稿 | 作者自查 | 完整度自检清单 |
| 评审中 | 阶段负责人 + 至少 1 名相关方 | 评审意见清单 |
| 已发布 | 全员 | 实施反馈 |

### 6. AI 协作约定

- AI **不得**直接修改现有文档内容（仅可建议）
- AI **不得**输出可运行的业务代码、可执行脚本
- AI 创建/补全文档**必须**遵循本规范与 [文档模板](01-文档模板.md)
- AI 发现新术语或现有文档矛盾，**必须**主动指出并给出修正建议

### 7. 反模式（禁止）

- ❌ 复制粘贴未经整理的聊天记录作为文档
- ❌ 大段截图代替文字（无法检索、无法版本控制）
- ❌ 缺少变更记录的"一次写定"文档
- ❌ 自造缩写或与术语表不一致的命名
- ❌ 文档内嵌个人信息（个人微信、手机号、邮箱），使用角色而非姓名
