### 错误现象

**错误表现**: 11 个分库导致跨库 JOIN 不可用、运维复杂度高；49 个 Flyway 迁移含过程态 ALTER/RENAME/DROP，维护成本高；9 份服务级 `schema.sql` + 8 份 `SchemaConfig.java` 重复维护；每个业务服务 pom 都依赖 `minimall-flyway-core`，classpath 含全 49 条迁移 → 每服务启动都跑全 49 条迁移到自己 DB（依赖 `IF NOT EXISTS` 幂等，浪费且易踩坑）。

**复现步骤**:

1. 检查 `minimall-flyway-core/src/main/resources/db/migration/` 下存在 49 个迁移文件（V1-V49）
2. 启动任一业务服务（如 `./mvnw -pl minimall-auth-service spring-boot:run`）
3. 观察日志：Flyway 在 auth_db 上执行全 49 条迁移（含与 auth 无关的 order/stock/notify 等表）
4. 跨库 JOIN 尝试：`SELECT * FROM auth_db.t_auth_user JOIN user_db.t_user ON ...` → MySQL 不允许跨库 JOIN（除非显式 `db.table` 写法），且微服务边界本就禁止跨库
5. 修改 V1-V49 中任一索引名为跨表重名（如 `idx_user`），运行 `./mvnw -pl minimall-order-service test` → H2 抛 `Index "IDX_USER" already exists`
6. `mvn install` 后启动 id-service → 报 `Found more than one migration with version 1`

### 根本原因分析

**直接原因**: 
1. 11 个分库（auth_db / user_db / merchant_db / goods_db / cart_db / stock_db / pay_db / order_db / notify_db / id_db + platform 无库走 Feign）按业务域切分，导致跨库 JOIN 不可用、运维复杂度高
2. 49 个 Flyway 迁移含过程态 ALTER/RENAME/DROP（如 V30 RENAME `t_user_auth → t_auth_user`、V12 `status VARCHAR → TINYINT`、V32 全表加 `version`），未在每次 ALTER 后回写初始 CREATE，历史包越积越多
3. 9 份服务级 `schema.sql` + 8 份 `SchemaConfig.java` 重复维护，未集中到共享 JAR
4. H2 `MODE=MySQL` 比真实 MySQL 更严格——要求索引名跨表全局唯一，原 V1-V49 中存在 9 个跨表重名索引

**根本原因**: 
1. 微服务初期按业务域分库，未考虑业务聚合查询需求与运维成本；待 QPS 真正上来前，分库带来的复杂性远大于收益
2. Flyway 迁移按时间演进累积，未在每次 ALTER 后回写初始 CREATE，未在迭代结束时合并历史 ALTER 为最终 CREATE
3. 服务级 `schema.sql` 重复维护，未集中到共享 JAR（`minimall-flyway-core`），导致 H2 兼容改写需在 9 处重复
4. H2 与 MySQL 在索引名唯一性约束上不一致，未统一用表前缀命名索引
5. Maven 构建机制理解不深：`mvn test`/`mvn install` 不做 clean，target/classes 残留旧文件会被打入 JAR

### 经验沉淀

**避免模式**:

1. **微服务初期按业务域分库**：未考虑业务聚合查询需求与运维成本。QPS 未达量级前，分库带来的跨库 JOIN 不可用、运维复杂度远大于收益。应统一单库 + schema 前缀区分业务域，待 QPS 上来再分库
2. **Flyway 迁移按时间累积过程态 ALTER**：未在每次 ALTER 后回写初始 CREATE，导致历史包越积越多（49 条迁移含 V30 RENAME、V12 ALTER、V32 全表 ADD version 等过程态）。维护成本高，新成员上手难
3. **服务级 schema.sql + SchemaConfig.java 重复维护**：未集中到共享 JAR，H2 兼容改写需在 9 处重复，任一处遗漏即单测失败
4. **H2 索引名跨表重名未规范化**：H2 `MODE=MySQL` 比真实 MySQL 更严格（要求索引名跨表全局唯一），原 V1-V49 中存在 9 个跨表重名索引（`idx_user` / `idx_status` / `idx_order`），未统一用表前缀命名
5. **Maven 构建机制理解不深**：`mvn test`/`mvn install` 不做 clean，target/classes 残留旧文件（如已删除的 schema.sql、V1-V49 迁移）会被打入 JAR 推到 `~/.m2`，导致下游服务启动报错（`Found more than one migration with version 1`）
6. **合并多份 SQL 时未用 `git rm` 删除原文件**：V49 是 untracked 文件，`git rm` 失败，需用文件删除方式清理；untracked 文件不会随 `git rm` 移除，易遗留

**最佳实践**:

1. **微服务初期统一单库**：用 schema 前缀区分业务域（如 `t_auth_xxx` / `t_order_xxx`），待 QPS 真正上来再分库。避免过早分库带来的复杂度
2. **Flyway 迁移每季度/迭代结束时合并历史 ALTER**：合并为最终 `CREATE TABLE IF NOT EXISTS`，控制迁移文件数。新成员上手只需读一份 V1 即可理解全库结构
3. **schema.sql 集中在共享 JAR**：`minimall-flyway-core` 提供共享 `schema.sql`，各服务 test profile 仅配置 `spring.sql.init.mode: always` + `schema-locations: classpath:schema.sql`，不维护服务级副本
4. **H2 索引统一用表前缀命名**：写 schema 时索引名统一用 `idx_<table>_<column>` / `uk_<table>_<column>` 格式，避免跨表重名踩坑（H2 `MODE=MySQL` 比真实 MySQL 更严格）
5. **跨模块修改共享 JAR 时使用 `mvn clean install`**：避免 target/classes 残留旧文件被打入 JAR 推到 `~/.m2`，导致下游服务启动报错
6. **合并多份 SQL 时优先用 `git rm` 删除原文件**：避免 untracked 文件遗留（V49 即是 untracked，导致 `git rm` 失败，需用文件删除方式清理）。提交前用 `git status --short` 复核，确保无 untracked 残留
